UI

דשבורד אדמין

+

המקום היחיד שבו אפליקציה נולדת או נמחקת.

  • יצירת אפליקציה — פותח את הטופס שהופך לקונפיגורציית ה-JSON.
  • עריכת מרכז הדאטה של אפליקציה קיימת.
  • מחיקת אפליקציה — צריכה למחוק ביחד דלי, KB, טבלה ושורת רג׳יסטרי.
UI

דשבורד פיתוח

+

התצוגה התפעולית, נפרדת מעבודת התוכן.

  • מוניטורינג — לכל אפליקציה: תנועה, שגיאות, סטטוס ingestion.
  • דיפלוי — הוצאת גרסה לאפליקציה אחת או לכולן.
UI

מרכז הדאטה

+

כאן הידע באמת חי, בצורה שאדם יכול לקרוא.

  • מציג את קבצי ה-markdown שיושבים בדלי של האפליקציה.
  • עריכת קובץ, ואז re-embedding לקובץ הזה בלבד.
  • יצירת קובץ חדש דרך מערכת חוקי מבנה, לא טקסט חופשי.
API

שירות ההקמה

+

הבקאנד שאליו הפרונט מוסר את ה-JSON.

  • קלט: JSON קונפיגורציה אחד. פלט: מזהי המשאבים של האפליקציה החדשה.
  • מריץ שבעה שלבים בסדר קבוע; כשלון באמצע משאיר יתומים, ולכן כל שלב צריך להיות הפיך.
  • אחראי על השמות: שם האפליקציה הוא המפתח שקושר בין הדלי, הטבלה ושורת הרג׳יסטרי.
S3

דלי האפליקציה

+

דלי אחד לכל אפליקציה — הפרדת דאטה מלאה בין פרויקטים.

  • נקרא על שם האפליקציה, נוצר ראשון כי כל השאר מצביע אליו.
  • מחזיק את קבצי ה-markdown — מקור האמת של מאגר הידע.
  • תיקון תוכן נעשה בקובץ כאן ומוזרם מחדש, אף פעם לא כטלאי בפרומפט.
BEDROCK

Knowledge Base ו-Data Source

+

נוצרים עם פרמטרים קבועים, כך שכל האפליקציות מאחזרות באותה צורה.

  • chunking — היררכי, הורה ~500 טוקנים / ילד ~150.
  • embeddings — Cohere Embed Multilingual v3, 1024 ממדים.
  • ה-Data Source מצביע על הדלי; ingestion job הופך קבצים לוקטורים.
DYNAMO

טבלת היסטוריית שיחה

+

טבלה משלה לכל אפליקציה.

  • מפתח לפי session id שנוצר בצד הלקוח; בלי חשבונות משתמש.
  • ההיסטוריה פגה לפי TTL, כך ששיחות לא נערמות.
DYNAMO

רג׳יסטרי המפעל

+

הטבלה היחידה שיודעת אילו אפליקציות קיימות.

  • שורה לכל אפליקציה: ui id, שם אפליקציה, מזהה Dynamo, מזהה KB.
  • שני הדשבורדים קוראים מכאן — בלי השורה, אפליקציה בלתי נראית גם אם המשאבים שלה קיימים.
